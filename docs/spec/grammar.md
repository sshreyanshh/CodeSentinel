# Mini-C++ Grammar Specification

## 1. Purpose

The lexical analyzer (lexer) converts the source code into a
sequence of tokens. This grammar specification defines the
valid sequences of tokens that form syntactically correct
programs in the Mini-C++ language supported by CodeSentinel.

The syntax analyzer (parser) uses this grammar to determine
whether the generated token sequence follows the language's
grammatical rules. For syntactically valid programs, the
parser also generates a parse tree representing their
grammatical structure.

The grammar is maintained in three places:

- `docs/spec/grammar.md`: Human-readable grammar specification.
- `backend/app/parser/grammar.py`: Grammar represented as
  Python data.
- `backend/app/parser/parser.py`: Hand-written recursive
  descent parser implementing the grammar.

These three representations must remain consistent.
Any disagreement between them may result in incorrect
syntax validation or parse-tree generation.

## 2. Formal Definition

A Context-Free Grammar (CFG) is formally represented as:

\[
G = (V, T, P, S)
\]

where:

- **V (Nonterminals):** A finite set of grammatical
  variables that represent language constructs, such as
  `Program`, `Stmt`, `Decl` and `Expr`.
- **T (Terminals):** A finite set of terminal symbols
  corresponding to the token types generated by the lexer,
  such as `KW_INT`, `IDENTIFIER`, `PLUS` and `SEMI`.
- **P (Productions):** A finite set of production rules
  that define how nonterminals can be expanded into
  terminals and other nonterminals.
- **S (Start Symbol):** The designated starting
  nonterminal from which the derivation of a complete
  program begins. For CodeSentinel, the start symbol is
  `Program`.

The grammar contains 36 nonterminals and 36 terminals
in the current backend implementation.

The following notation is used throughout this document:

| Notation | Meaning |
|---|---|
| `→` | Produces or derives |
| `\|` | Alternative production |
| `ε` | Empty string |
| `*` | Zero or more repetitions (EBNF only) |
| `?` | Optional occurrence (EBNF only) |
| `EOF` | End-of-input token |

## 3. Language Scope

CodeSentinel supports a restricted programming language
based on a subset of C++, referred to as Mini-C++.

The current grammar defines a program as a single
function-like entry point consisting of the `int` keyword,
an identifier, an empty parameter list and a function body
enclosed in braces.

The supported language constructs include:

- **Data types:** `int`, `float`, `bool` and `char`.
- **Variable declarations:** Declarations with or without
  initial values.
- **Assignments:** Assignment of expressions to identifiers.
- **Conditional statements:** `if` and optional `else`.
- **Loops:** `while` and `for`.
- **Return statements:** Return statements with an optional
  expression.
- **Nested blocks:** Statements enclosed within braces.
- **Expressions:** Arithmetic, relational, equality and
  logical expressions.
- **Unary operators:** Logical NOT (`!`) and unary minus (`-`).

The current grammar does not support:

- Multiple function definitions or function parameters.
- Arrays and pointers.
- Classes and objects.
- String literals.
- `switch` statements.
- Increment and decrement operators (`++`, `--`).
- Compound assignment operators (`+=`, `-=`, etc.).
- Preprocessor directives.

This specification describes syntactic support only.
Semantic checks, such as variable declaration validation
and type compatibility, are outside the responsibility
of the current CFG-based parser.


## 4. Productions

The productions define the syntactic structure of the supported Mini-C++ language. They specify how terminals and nonterminals can be combined to form valid programs.

Two representations of the grammar are provided:

- **Readable Form (EBNF):** Uses repetition and optionality shortcuts to make the grammar easier to understand.
- **Pure Context-Free Form (BNF):** Uses explicit production rules and helper nonterminals without EBNF shortcuts. This is the representation maintained in `backend/app/parser/grammar.py`.

Both representations describe the same language and must remain consistent with the recursive descent parser.

### 4.1 Readable Form (EBNF)

The following EBNF representation describes the syntactic structure of Mini-C++. It uses `*` to represent zero or more repetitions and `?` to represent optional elements.

```text
Program     → KW_INT IDENTIFIER LPAREN RPAREN Block EOF

Block       → LBRACE Stmt* RBRACE

Stmt        → Decl SEMI
            | Assign SEMI
            | IfStmt
            | WhileStmt
            | ForStmt
            | ReturnStmt
            | Block
            | SEMI

Decl        → Type IDENTIFIER ( ASSIGN Expr )?

Type        → KW_INT | KW_FLOAT | KW_BOOL | KW_CHAR

Assign      → IDENTIFIER ASSIGN Expr

IfStmt      → KW_IF LPAREN Expr RPAREN Stmt
              ( KW_ELSE Stmt )?

WhileStmt   → KW_WHILE LPAREN Expr RPAREN Stmt

ForStmt     → KW_FOR LPAREN ( Decl | Assign )?
              SEMI Expr? SEMI Assign? RPAREN Stmt

ReturnStmt  → KW_RETURN Expr? SEMI

Expr        → OrExpr

OrExpr      → AndExpr ( OR AndExpr )*

AndExpr     → EqExpr ( AND EqExpr )*

EqExpr      → RelExpr ( (EQ | NEQ) RelExpr )*

RelExpr     → AddExpr ( (LT | GT | LE | GE) AddExpr )*

AddExpr     → MulExpr ( (PLUS | MINUS) MulExpr )*

MulExpr     → Unary ( (STAR | SLASH | PERCENT) Unary )*

Unary       → (NOT | MINUS) Unary | Primary

Primary     → IDENTIFIER
            | INT_LITERAL
            | FLOAT_LITERAL
            | CHAR_LITERAL
            | KW_TRUE
            | KW_FALSE
            | LPAREN Expr RPAREN
```

`EOF` represents the end-of-input token. It is matched during parsing but is not included in the parse tree.

### 4.2 Pure Context-Free Form (BNF)

The EBNF representation uses repetition (`*`) and optionality (`?`) shortcuts. These shortcuts are replaced by helper nonterminals and epsilon (`ε`) productions in the pure CFG representation.

For example, the EBNF production:

```text
StmtList → Stmt*
```

is represented in pure CFG form as:

```text
StmtList → Stmt StmtList | ε
```

Similarly, optional declaration initialization:

```text
DeclInit → ASSIGN Expr | ε
```

The complete pure CFG production set used by the backend is given below.

```text
Program    → KW_INT IDENTIFIER LPAREN RPAREN Block EOF

Block      → LBRACE StmtList RBRACE

StmtList   → Stmt StmtList | ε

Stmt       → Decl SEMI
           | Assign SEMI
           | IfStmt
           | WhileStmt
           | ForStmt
           | ReturnStmt
           | Block
           | SEMI

Decl       → Type IDENTIFIER DeclInit

DeclInit   → ASSIGN Expr | ε

Type       → KW_INT
           | KW_FLOAT
           | KW_BOOL
           | KW_CHAR

Assign     → IDENTIFIER ASSIGN Expr

IfStmt     → KW_IF LPAREN Expr RPAREN Stmt ElsePart

ElsePart   → KW_ELSE Stmt | ε

WhileStmt  → KW_WHILE LPAREN Expr RPAREN Stmt

ForStmt    → KW_FOR LPAREN ForInit SEMI ForCond SEMI
             ForStep RPAREN Stmt

ForInit    → Decl | Assign | ε

ForCond    → Expr | ε

ForStep    → Assign | ε

ReturnStmt → KW_RETURN ReturnVal SEMI

ReturnVal  → Expr | ε

Expr       → OrExpr

OrExpr     → AndExpr OrTail

OrTail     → OR AndExpr OrTail | ε

AndExpr    → EqExpr AndTail

AndTail    → AND EqExpr AndTail | ε

EqExpr     → RelExpr EqTail

EqTail     → EqOp RelExpr EqTail | ε

EqOp       → EQ | NEQ

RelExpr    → AddExpr RelTail

RelTail    → RelOp AddExpr RelTail | ε

RelOp      → LT | GT | LE | GE

AddExpr    → MulExpr AddTail

AddTail    → AddOp MulExpr AddTail | ε

AddOp      → PLUS | MINUS

MulExpr    → Unary MulTail

MulTail    → MulOp Unary MulTail | ε

MulOp      → STAR | SLASH | PERCENT

Unary      → NOT Unary
           | MINUS Unary
           | Primary

Primary    → IDENTIFIER
           | INT_LITERAL
           | FLOAT_LITERAL
           | CHAR_LITERAL
           | KW_TRUE
           | KW_FALSE
           | LPAREN Expr RPAREN
```

In the pure CFG representation:

- Each nonterminal represents a grammatical construct.
- Each terminal corresponds to a token type generated by the lexical analyzer.
- The symbol `ε` represents the empty string and is implemented as an empty production (`[]`) in `grammar.py`.
- Helper nonterminals such as `StmtList`, `DeclInit`, `ElsePart` and the expression tail productions represent repetition and optionality without requiring EBNF shortcuts.

The expression grammar uses separate precedence levels and right-recursive tail productions to avoid left recursion. This makes the grammar suitable for implementation using recursive descent parsing.

The productions in this section correspond to the grammar data maintained in `backend/app/parser/grammar.py`. The grammar documentation, grammar data and parser implementation must remain synchronized.


## 5. Operator Precedence and Associativity

Operator precedence and associativity determine how expressions containing multiple operators are grouped during parsing.

In Mini-C++, different operators have different precedence levels. Operators with higher precedence are grouped before operators with lower precedence. When operators have the same precedence, associativity determines their grouping.

### 5.1 Operator Precedence

The expression grammar is divided into multiple levels, ranging from logical OR at the lowest precedence to unary operators at the highest precedence.

| Precedence Level | Operators | Description |
|---|---|---|
| 1 (Lowest) | `||` | Logical OR |
| 2 | `&&` | Logical AND |
| 3 | `==`, `!=` | Equality and inequality |
| 4 | `<`, `>`, `<=`, `>=` | Relational operators |
| 5 | `+`, `-` | Addition and subtraction |
| 6 | `*`, `/`, `%` | Multiplication, division and modulo |
| 7 (Highest) | `!`, unary `-` | Unary operators |

The grammar implements precedence through separate nonterminals for each expression level:

```text
OrExpr  → AndExpr OrTail
AndExpr → EqExpr AndTail
EqExpr  → RelExpr EqTail
RelExpr → AddExpr RelTail
AddExpr → MulExpr AddTail
MulExpr → Unary MulTail
Unary   → NOT Unary | MINUS Unary | Primary
```

Each lower-precedence expression level calls the next higher-precedence level. This hierarchical structure ensures that operators with higher precedence are grouped before operators with lower precedence.

**Examples:**

1. Arithmetic precedence:

   ```cpp
   1 + 2 * 3
   ```

   The expression is grouped as:

   \[
   1 + (2 \times 3)
   \]

   Multiplication has higher precedence than addition.

2. Logical precedence:

   ```cpp
   a || b && c
   ```

   The expression is grouped as:

   \[
   a \ || \ (b \land c)
   \]

   Logical AND has higher precedence than logical OR.

3. Relational and equality precedence:

   ```cpp
   a < b == c < d
   ```

   The expression is grouped as:

   \[
   (a < b) == (c < d)
   \]

   Relational operators have higher precedence than equality operators.

### 5.2 Associativity

Associativity determines how operators of the same precedence level are grouped when they appear consecutively in an expression.

The two common forms of associativity are:

- **Left Associativity:** Operators are grouped from left to right.
- **Right Associativity:** Operators are grouped from right to left.

In the current Mini-C++ grammar, binary operators are left-associative, while unary operators are right-associative.

**Left-associative examples:**

1. Subtraction:

   ```cpp
   a - b - c
   ```

   The expression is grouped as:

   \[
   (a-b)-c
   \]

2. Division:

   ```cpp
   a / b / c
   ```

   The expression is grouped as:

   \[
   (a/b)/c
   \]

**Right-associative example:**

Consider consecutive unary logical NOT operators:

```cpp
!!a
```

The expression is grouped as:

\[
!(!a)
\]

Similarly, nested unary minus operations:

```cpp
-(-a)
```

are parsed from the innermost unary expression outward.

The grammar implements right associativity for unary operators through the recursive production:

```text
Unary → NOT Unary
      | MINUS Unary
      | Primary
```

### 5.3 Summary of Operator Precedence and Associativity

| Precedence Level | Operators | Associativity |
|---|---|---|
| 1 | `||` | Left |
| 2 | `&&` | Left |
| 3 | `==`, `!=` | Left |
| 4 | `<`, `>`, `<=`, `>=` | Left |
| 5 | `+`, `-` | Left |
| 6 | `*`, `/`, `%` | Left |
| 7 | Unary `!`, unary `-` | Right |

The expression grammar ensures that expressions are parsed according to these precedence and associativity rules. This allows CodeSentinel to construct the appropriate hierarchical representation of expressions in its parse trees.


## 6. Ambiguity: The Dangling Else

### 6.1 What Is the Dangling Else Problem?

The dangling else problem is a grammatical ambiguity that occurs when an `if` statement is nested inside another `if` statement and an `else` clause appears.

Consider the following Mini-C++ code:

```cpp
if (a)
    if (b)
        x = 1;
    else
        x = 2;
```

The `else` clause can theoretically be associated with either the inner `if` statement or the outer `if` statement.

This creates two possible interpretations:

**Interpretation 1: `else` belongs to the inner `if`.**

```cpp
if (a) {
    if (b)
        x = 1;
    else
        x = 2;
}
```

**Interpretation 2: `else` belongs to the outer `if`.**

```cpp
if (a) {
    if (b)
        x = 1;
}
else {
    x = 2;
}
```

### 6.2 Resolution in Mini-C++

Mini-C++ follows the conventional rule that an `else` clause is associated with the nearest unmatched `if` statement.

Therefore, in the example above, the `else` belongs to the inner `if` statement.

This rule ensures consistent interpretation of nested conditional statements.

### 6.3 Grammar and Parser Behavior

The grammar represents an optional `else` clause using the following production:

```text
IfStmt   → KW_IF LPAREN Expr RPAREN Stmt ElsePart
ElsePart → KW_ELSE Stmt | ε
```

The `ElsePart` production allows an `if` statement to have an optional `else` clause.

However, this production introduces an LL(1) conflict because `KW_ELSE` can be considered both:

- The beginning of an `else` clause.
- A possible token in the FOLLOW set of `ElsePart`.

The parser resolves this ambiguity by checking for `KW_ELSE` immediately after parsing the body of an `if` statement.

If `KW_ELSE` is present, it is consumed and associated with that `if` statement.

This implements the nearest unmatched `if` rule.

### 6.4 Summary

| Aspect | Project decision |
|---|---|
| Problem | Ambiguous association of `else` in nested `if` statements |
| Resolution rule | `else` belongs to the nearest unmatched `if` |
| Grammar production | `ElsePart → KW_ELSE Stmt | ε` |
| Parser behavior | Checks for `KW_ELSE` immediately after parsing the `if` body |
| LL(1) analysis | One conflict involving `ElsePart` and `KW_ELSE` |

> The dangling else conflict is an intentional grammar ambiguity resolved by the recursive descent parser.


## 7. FIRST and FOLLOW Sets

FIRST and FOLLOW sets are used in grammar analysis to determine which terminals can appear at particular positions during derivation. They are also important for checking whether a grammar satisfies the LL(1) condition.

### 7.1 FIRST Set

The FIRST set of a grammar symbol `X`, written as `FIRST(X)`, contains the terminals that can appear at the beginning of any string derived from `X`.

If `X` can derive the empty string, `ε` is also included in its FIRST set.

For example, consider the production:

```text
Type → KW_INT | KW_FLOAT | KW_BOOL | KW_CHAR
```

Therefore:

```text
FIRST(Type) = {KW_INT, KW_FLOAT, KW_BOOL, KW_CHAR}
```

### 7.2 FOLLOW Set

The FOLLOW set of a nonterminal `X`, written as `FOLLOW(X)`, contains the terminals that can appear immediately after `X` in a sentential form.

For example, consider:

```text
Stmt → Decl SEMI
```

Since `SEMI` appears immediately after `Decl`, it belongs to `FOLLOW(Decl)`.

Therefore:

```text
SEMI ∈ FOLLOW(Decl)
```

The end-of-input marker `$` is included in the FOLLOW set of the start symbol.

### 7.3 FIRST and FOLLOW Tables

The following table shows selected FIRST and FOLLOW sets from the grammar analysis.

| Nonterminal | FIRST | FOLLOW |
|---|---|---|
| `Program` | `KW_INT` | `$` |
| `Stmt` | `IDENTIFIER`, `KW_INT`, `KW_FLOAT`, `KW_BOOL`, `KW_CHAR`, `KW_IF`, `KW_WHILE`, `KW_FOR`, `KW_RETURN`, `LBRACE`, `SEMI` | FIRST(Stmt), `KW_ELSE`, `RBRACE` |
| `StmtList` | FIRST(Stmt), `ε` | `RBRACE` |
| `Decl` | `KW_INT`, `KW_FLOAT`, `KW_BOOL`, `KW_CHAR` | `SEMI` |
| `DeclInit` | `ASSIGN`, `ε` | `SEMI` |
| `ElsePart` | `KW_ELSE`, `ε` | Same as FOLLOW(Stmt), including `KW_ELSE` |
| `Expr` | `IDENTIFIER`, `INT_LITERAL`, `FLOAT_LITERAL`, `CHAR_LITERAL`, `KW_TRUE`, `KW_FALSE`, `LPAREN`, `NOT`, `MINUS` | `SEMI`, `RPAREN` |
| `AddTail` | `PLUS`, `MINUS`, `ε` | `OR`, `AND`, `EQ`, `NEQ`, `LT`, `GT`, `LE`, `GE`, `RPAREN`, `SEMI` |
| `MulTail` | `STAR`, `SLASH`, `PERCENT`, `ε` | FOLLOW(AddTail), `PLUS`, `MINUS` |
| `Primary` | `IDENTIFIER`, `INT_LITERAL`, `FLOAT_LITERAL`, `CHAR_LITERAL`, `KW_TRUE`, `KW_FALSE`, `LPAREN` | Binary operators, `RPAREN`, `SEMI` |

**Note:** This is a selected table, not the complete FIRST/FOLLOW table. The complete table must contain every nonterminal defined in `parser/grammar.py`.

### 7.4 Computation of FIRST and FOLLOW Sets

The FIRST and FOLLOW sets are computed programmatically by:

```text
backend/app/parser/analysis.py
```

Whenever the grammar is modified, these sets should be regenerated to ensure that the documentation remains consistent with the implementation.

The generated results should be included in this specification so that the grammar can be independently reviewed.


## 8. LL(1) Analysis

### 8.1 What Is an LL(1) Grammar?

LL(1) is a parsing technique in which:

- The first `L` represents scanning the input from left to right.
- The second `L` represents constructing a leftmost derivation.
- The `1` represents using one lookahead token to select the appropriate production.

An LL(1) grammar allows a parser to determine which production to apply by examining only the next input token.

### 8.2 LL(1) Conflicts

An LL(1) conflict occurs when the parser cannot uniquely select a production using a single lookahead token.

Such conflicts are identified by examining the FIRST and FOLLOW sets of the grammar productions.

### 8.3 LL(1) Analysis of Mini-C++

The grammar analysis implemented in `backend/app/parser/analysis.py` reports exactly one conflict:

| Nonterminal | Conflicting token |
|---|---|
| `ElsePart` | `KW_ELSE` |

The conflict arises from the following production:

```text
ElsePart → KW_ELSE Stmt | ε
```

`KW_ELSE` can begin the first alternative. However, it also belongs to `FOLLOW(ElsePart)`, creating a conflict when selecting between the two alternatives.

This is the dangling else ambiguity discussed in Section 6.

### 8.4 Conflict Resolution

The recursive descent parser resolves this ambiguity by checking for `KW_ELSE` immediately after parsing the body of an `if` statement.

If `KW_ELSE` is present, it is consumed and associated with the nearest unmatched `if` statement.

This ensures consistent interpretation of nested conditional statements.

### 8.5 Summary

The grammar analysis reports exactly one LL(1) conflict, involving `ElsePart` and `KW_ELSE`.

All other nonterminals are reported as conflict-free by the current grammar analysis.

The parser explicitly handles the dangling else ambiguity using the nearest unmatched `if` rule.

The grammar tests in `backend/tests/parser/` help ensure that no unexpected LL(1) conflicts are introduced when the grammar is modified.


## 9. Worked Leftmost Derivations

A leftmost derivation is a sequence of grammar-production applications in which the leftmost nonterminal is expanded at every step.

The symbol `⇒` represents a derivation in one step.

### 9.1 Example A: Empty Program

Consider the following Mini-C++ program:

```cpp
int main() {
}
```

Its token sequence is:

```text
KW_INT IDENTIFIER LPAREN RPAREN LBRACE RBRACE EOF
```

Using the grammar, the leftmost derivation is:

```text
Program
⇒ KW_INT IDENTIFIER LPAREN RPAREN Block EOF
⇒ KW_INT IDENTIFIER LPAREN RPAREN LBRACE StmtList RBRACE EOF
⇒ KW_INT IDENTIFIER LPAREN RPAREN LBRACE RBRACE EOF
```

The final string contains only terminals and represents the complete token sequence of the program.

### 9.2 Example B: Arithmetic Expression

Consider the expression:

```cpp
1 + 2
```

Its leftmost derivation using the expression grammar is:

```text
Expr
⇒ OrExpr
⇒ AndExpr
⇒ EqExpr
⇒ RelExpr
⇒ AddExpr
⇒ MulExpr AddTail
⇒ Unary MulTail AddTail
⇒ Primary MulTail AddTail
⇒ INT_LITERAL MulTail AddTail
⇒ INT_LITERAL AddTail
⇒ INT_LITERAL AddOp MulExpr AddTail
⇒ INT_LITERAL PLUS MulExpr AddTail
⇒ INT_LITERAL PLUS Unary MulTail AddTail
⇒ INT_LITERAL PLUS Primary MulTail AddTail
⇒ INT_LITERAL PLUS INT_LITERAL MulTail AddTail
⇒ INT_LITERAL PLUS INT_LITERAL AddTail
⇒ INT_LITERAL PLUS INT_LITERAL
```

Here, `INT_LITERAL` represents the numeric literals `1` and `2`, respectively.

The derivation demonstrates how the expression grammar recognizes an arithmetic expression while preserving operator precedence.

### 9.3 Purpose of Worked Derivations

These examples demonstrate how valid token sequences can be generated from the start symbol or an expression nonterminal using the grammar productions.

They also provide a way to manually verify whether the grammar correctly describes the supported Mini-C++ constructs.

## 10. Parse Tree Shape

The parser generates a parse tree for syntactically valid input.

The parse tree represents the hierarchical structure of the input according to the grammar productions.

### 10.1 Nodes and Leaves

The parse tree contains:

- **Nonterminal nodes:** Represent grammar symbols such as `Program`, `Block`, `Stmt`, and `Expr`.
- **Terminal leaves:** Represent the tokens recognized by the lexer.

The leaves, when read from left to right, reproduce the original token sequence, excluding `EOF`.

### 10.2 Expression Parse Tree

For example, consider:

```cpp
1 + 2
```

The expression is represented using the expression grammar and its corresponding precedence levels.

The `AddExpr` level represents the addition operation, while the operands are represented through the lower-level expression productions.

### 10.3 Parse Tree Simplification

The implementation uses a simplified representation for expression precedence levels.

A binary-operator tier (`OrExpr` through `MulExpr`) is included only when an operator is present at that level.

For example, an expression containing only an identifier can be represented as:

```text
Expr
└── Primary
    └── IDENTIFIER
```

This avoids unnecessary intermediate nodes when an expression does not contain an operator at a particular precedence level.

**Note:** This simplification is a design decision to be confirmed by the team against the final implementation.

## 11. Valid and Invalid Examples

The following examples demonstrate some valid and invalid programs according to the Mini-C++ grammar.

### 11.1 Valid Programs

| Input | Reason |
|---|---|
| `int main() { }` | Empty block is allowed. |
| `int main() { int a = 1 + 2; }` | Declaration with an initializer is allowed. |
| `int main() { for (;;) { } }` | All three parts of a `for` loop are optional. |

### 11.2 Invalid Programs

| Input | Reason |
|---|---|
| `int main() { int a = ; }` | An expression is expected after `ASSIGN`. |
| `int main() { int a = 1 }` | A semicolon is expected after the declaration. |
| `main() { }` | A program must begin with `KW_INT`. |
| `int main() { a = 1;` | The closing `RBRACE` is missing at the end of input. |

## 12. Syntax Error Behavior

The parser is responsible for identifying syntax errors when the input token sequence does not conform to the defined Mini-C++ grammar.

### 12.1 Error Reporting

The parser reports the **first syntax error** encountered during parsing and stops further parsing.

A syntax error contains the following information:

- **Error code:** Identifies the type of syntax error.
- **Source location:** Indicates the line and column of the offending token.
- **Expected tokens:** Lists the token types that would have been valid at that position.

The parser uses the following syntax error codes:

| Error Code | Description |
|---|---|
| `SYN_UNEXPECTED_TOKEN` | An unexpected token was encountered during parsing. |
| `SYN_UNEXPECTED_EOF` | The input ended unexpectedly while the parser was expecting another token. |

### 12.2 Interaction with Lexical Analysis

The parser runs only when lexical analysis completes without reporting lexical errors.

If the lexer reports one or more lexical errors, parsing is skipped.

This ensures that the parser receives a valid token stream as its input.
